Stage 4 · Architecture Document
System Architecture
How the layers are arranged and why each decision was made

System Overview

The Smart Corporate Equipment & Asset Reservation System is designed to manage high-value asset checkout processes with strict governance and automated rule enforcement. It is a lightweight, responsive web application combining a clean REST API backend with a modern HTML5 / Vanilla CSS frontend styled as a physical inventory ledger.

System Components

  • Frontend UI — Presentation Layer
    Built with Vanilla HTML5, CSS3 (Glassmorphism / ledger aesthetics), and JavaScript. Responsible for rendering real-time asset availability, handling user input, client-side validation, and asynchronously fetching data from the API.
  • API Server — Application Layer
    Node.js backend using Express.js. Handles core business logic, input sanitisation, security validation (XSS / injection checks), rate-limiting, and RESTful routing.
  • Data Store — Data Layer
    An encapsulated module (database.js) backed by flat CSV files (assets.csv / reservations.csv) via csv-parse and csv-stringify. Provides decoupled create, find, and cancel operations. CSV storage was deliberately chosen so that reviewers can inspect the data directly in Excel without any database provisioning.

Data Flow

  1. User Action — the user selects an asset and submits a reservation date range via the UI.
  2. Client Validation — the frontend checks that dates are valid (start ≥ today, end > start).
  3. API Request — a POST request with assetId, userId, startDate, and endDate is sent to the backend.
  4. Server Validation — the server validates constraints:
    • Is it in the past?
    • Is it XSS / SQL-injection safe?
    • Does it overlap with existing reservations for that asset?
    • Does the duration exceed the asset's max limit?
    • Does it exceed the user's active quota?
  5. Data Mutation — if valid, the Data Store creates a reservation record and assigns an ID and APPROVED (or PENDING_APPROVAL) status.
  6. Response — server responds with 201 Created and the new object.
  7. UI Update — the frontend displays a success toast and reloads the active reservations view.

Technology Choices

Technology Choice Rationale
Backend Node.js + Express Fast scaffolding, non-blocking I/O ideal for API servers, universally understood.
Frontend Vanilla JS / HTML / CSS Eliminates build steps; code runs directly from the browser without compilation.
Testing Jest + Supertest Robust assertion and mocking library; Supertest allows HTTP endpoint testing without a live port.
Architecture Monolithic MVC-like Single repository with separated routing, logic, and data layers — the right balance for this scope without over-engineering.

Trade-offs & Known Limitations

CSV-Backed Persistence

The application uses database.js backed by flat CSV files instead of a relational DB. This allows reviewers to instantly inspect live data in Excel or Google Sheets, fitting the ledger theme. To prevent data corruption under concurrent load (e.g., the rate-limit stress tests), the architecture uses an asynchronous write queue and atomic file rename operations (fs.renameSync) — writing to a .tmp file first and flipping it over the real file, so a mid-write crash cannot produce a half-written, unparseable CSV.

File Isolation

When NODE_ENV=test, the database module targets test-assets.csv and test-reservations.csv so running the Jest suite never blows away your live demo data.

Authentication

Roles (?role=admin) and the Login Screen are purely frontend constructs to facilitate demo flows. Anyone can type any name and check the Admin box without cryptographic verification. This is an intentional simplification. The backend continues to strictly validate and sanitise all payloads, rejecting XSS patterns and blank names regardless of role.

API Design & Data Models
Data shapes, validation lifecycle, and error contract

Data Models

Asset

Represents an inventoriable piece of corporate equipment.

  • id (String) — Unique identifier, e.g. "A1"
  • name (String) — Display name of the equipment
  • category (String) — Grouping category: Computing, Photography, Displays, Misc
  • status (Enum) — AVAILABLE or MAINTENANCE
  • maxDuration (Integer) — Maximum allowed checkout duration in days

Reservation

Represents a user's booking for an asset.

  • id (String) — Auto-incremented ID, e.g. "R1"
  • assetId (String) — Foreign key to the Asset
  • userId (String) — Name & registration of the person who booked
  • startDate (Date) — Start date of checkout (stored as ISO string in CSV)
  • endDate (Date) — End date of checkout
  • status (Enum) — APPROVED, PENDING_APPROVAL, CANCELLED, RETURNED
  • createdAt (Date) — Timestamp of creation

API Endpoints

GET /api/assets

Retrieve the full catalog of assets, including their current status.

Response: 200 OK — Array of Asset objects.

POST /api/assets

Create a new asset in the inventory.

Payload: { "name": "...", "category": "...", "maxDuration": 14 }

Response: 201 Created with the created Asset object.

DELETE /api/assets/:id

Permanently remove an asset from the inventory.

Response: 200 OK or 404 Not Found.

PATCH /api/assets/:id/maintenance

Toggle an asset's status between AVAILABLE and MAINTENANCE.

Response: 200 OK with updated Asset object.

GET /api/assets/:id/history

Retrieve the full reservation history for a given asset, sorted newest-first.

Response: 200 OK — Array of Reservation objects, or 404 if asset does not exist.

POST /api/reservations

Create a new reservation. This is the primary business-logic endpoint — every request passes through a multi-stage validation gauntlet.

Payload: { "assetId": "A1", "userId": "NAME-REG123", "startDate": "YYYY-MM-DD", "endDate": "YYYY-MM-DD" }

Success Response: 201 Created with the Reservation object (status will be either APPROVED or PENDING_APPROVAL).

POST /api/reservations/:id/cancel

Cancel an active reservation, freeing the asset for other users.

Response: 200 OK { "message": "Reservation cancelled successfully." }

Reservation Validation Lifecycle

The POST /api/reservations endpoint acts as a strict security and business-logic gatekeeper. Each stage gates the next — a request must pass all of them before a record is created.

Validation Order

XSS Safety → Date Validity → Maintenance Check → Duration Cap → Quota Check → Overlap Check → Save

  • XSS / Injection Safety — rejects payloads containing ' " < > ;
  • Date Validity — rejects past dates and invalid ranges (end ≤ start)
  • Maintenance Check — rejects requests for assets currently in maintenance
  • Duration Cap — rejects requests where (endDate − startDate) exceeds asset.maxDuration
  • Quota Check — if the user already has 2 active reservations, the new one is created with status PENDING_APPROVAL rather than failing
  • Overlap Check — rejects requests where the asset is already booked for the requested dates
  • Rate Limiting — the endpoint is rate-limited to 50 requests per minute per IP

Error Handling Matrix

All errors return a consistent JSON envelope: {"error": "Description"}

AI-Assisted Change Loop
Feature request → regression → self-correction, documented end-to-end

Feature Request

The Prompt Given to the AI

"When a user exceeds their quota of 2 active reservations, instead of returning a 400 Bad Request error, create the reservation but set its status to PENDING_APPROVAL for admin review."

Code Changes Made by AI

The AI modified the quota validation logic in src/server.js. Rather than hard-rejecting quota overflows, it extracts the would-be status into a variable before reaching the database write:

JS — server.js// BEFORE — hard 400 rejection on 3rd booking
const userReservations = db.getReservationsByUser(userId);
if (userReservations.length >= 2) {
  return res.status(400).json({ error: 'User quota exceeded.' });
}

// AFTER — quota overflow creates PENDING_APPROVAL instead
const userReservations = db.getReservationsByUser(userId);
let finalStatus = 'APPROVED';
if (userReservations.length >= 2) {
  finalStatus = 'PENDING_APPROVAL';
}
// ... date validation, overlap check ...
const reservation = db.createReservation({ assetId, userId, startDate, endDate });
reservation.status = finalStatus;
res.status(201).json(reservation);

Detecting the Regression — Red Run

Upon running the existing test suite (npm test), the automated system caught a regression. The test written to enforce the hard 400 limit failed because it now received a 201.

Red Run Captured

AI Self-Correction — Green Run

The AI recognised that the feature change fundamentally altered the expected business rules for quota limits. It corrected the test suite to expect the new intended behaviour:

JS — api.test.js// BEFORE — expected hard rejection
const res = await request(app).post('/api/reservations').send(payload3);
expect(res.statusCode).toBe(400);
expect(res.body.error).toContain('User quota exceeded');

// AFTER — expects PENDING_APPROVAL, not failure
const res = await request(app).post('/api/reservations').send(payload3);
expect(res.statusCode).toBe(201);
expect(res.body.status).toBe('PENDING_APPROVAL');
Green Run — All 15 Tests Pass
Final Outcome

Running npm test after the correction resulted in a completely passing test suite, successfully closing the loop. Full logs are in test-reports/03_healed_pass.log.
